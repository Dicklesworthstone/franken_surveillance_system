# Export and natively verify retained RTP receipt streams

The `fss-decode-rtp receipts` and `verify-receipts` commands compose the existing retained
source recovery, current-custody decoder, privacy masks and canonical frame receipts. They
are operator utilities, not a second media decoder or a new source of authority. Existing
`inspect` and `decode` behavior remains available, including default snapshot decoding.

## Export

```sh
fss-decode-rtp receipts --root DEPLOYMENT --site SITE --source-root sha256:ROOT \
  --custody current --receipts-out FRAMES.receipts --output FRAMES.pgm
```

`--output` is optional. `--receipts-out` is required. Both destinations must be different new
files outside the deployment, with existing owner-protected parent directories. No parent
or deployment directory is created. The command streams each privacy-projected frame to the
existing bounded PGM writer and its canonical receipt to a separate bounded writer. Unix
outputs are created with mode 0600. Linux output creation is relative to a pinned directory
handle; other platforms retain the existing protected-directory trust boundary. File and
parent synchronization complete before success is reported.

On success, retain the reported `receipts_sha256` independently, together with the exact
source root, parameter selection, decode options and `receipt_recipe`. Decode counters,
receipt bytes, frame-receipt payload bytes and current-custody read bytes are reported
separately. No manifest, frame or receipt is implicitly published into deployment authority.

## Verify from cold custody

```sh
fss-decode-rtp verify-receipts --root DEPLOYMENT --site SITE --source-root sha256:ROOT \
  --custody current --receipts-in FRAMES.receipts --receipts-sha256 sha256:EXPECTED
```

Verification requires an independently supplied SHA-256 and accepts no output paths. It
reopens the retained root, checks current custody and privacy, reproduces native H.264 output,
and regenerates the complete receipt stream from explicit owner-selected configuration.
Saved bytes are compared incrementally with those regenerated bytes. Saved lengths, counts,
configuration fields and success claims never control allocation or grant decode authority.
The independently expected digest and exact final EOF must also agree.

Use the same `--sps`, `--pps`, receiver/decoder options and native limits used for export;
those values are part of pixel interpretation. An omitted SPS/PPS pair is accepted only when
one unambiguous in-source pair exists. Different native limits or a changed current privacy
policy intentionally change the receipt identity. Old receipts are historical observations,
not permission to bypass the current policy. Rehashing changed, truncated, reordered,
duplicated or appended input does not make it equal to native reproduction.

Both commands require explicit `--custody current`; neither falls back to a cached snapshot.
The existing source, recovery, decode, output, source-span and progress limits still apply.
`--max-custody-read-bytes` remains separate from initial recovery's `--max-read-bytes`.
Additional bounds are `--max-receipt-bytes` (default 1 MiB, maximum 8 MiB) and
`--max-receipts-bytes` (default 32 MiB, maximum 256 MiB, including all stream framing).
Whole-graph custody readback is deliberately conservative and expensive; this is a bounded
forensic/preview profile, not a long-recording throughput claim.

## Complete-stream contract

The stream domain is `fss.retained_rtp_h264_receipt_stream.v1`. Canonical framing holds a
versioned root header, display-order frame records with ordinals and exact unchanged frame
receipt bytes, and one terminal record binding native accounting and the interpretation
recipe. The terminal record is emitted only after complete decoding and drain with at least
one frame and no refusals or skipped groups. A receipt for one successful frame cannot prove
that the entire recording was decoded. See `rtp_frame_receipts.md` for each frame's exact
source-to-pixels binding and its conservative capture-time semantics.

Library entrypoints are `write_receipt_stream`, `write_receipt_stream_with_frames` and
`verify_receipt_stream` in `ingest::rtpdump::receipt_stream`. They use bounded 4 KiB I/O,
explicit cancellation checkpoints, bounded interruption retries and whole-record admission.
The optional synchronous frame consumer sees only the existing masked frame type. Its
failure stops decoding and prevents successful stream completion. Caller I/O errors do not
become successful shorter-prefix summaries.

Receipt and PGM files are not a two-file atomic transaction. Cancellation, late source
failure, I/O or sync failure may leave one or both files, including partial bytes. A nonzero
exit and `receipts_complete=false` or `receipts_verified=false` never certify those files;
there is no automatic deletion or overwrite of a previous result. PGM output is not accepted
as verification input by this command. Checking a separate PGM requires comparing its bytes
with fresh native output; receipt verification alone does not inspect that PGM file.

## Executed validation and remaining scope

Eight real-fixture library tests cover cold reproduction, short I/O, native comparison,
changed recipes and masks, tampering and truncation, reordering and duplication, quotas,
partial source, cancellation and sink failures. Three parser tests and six real-process CLI
tests cover export/verification, PGM equivalence, unchanged authority, private files, path
collisions, limits, malformed requests, current privacy and incomplete source.

These tests were executed successfully using pinned nightly-2026-08-31 recovered from the
repository's SHA-256-verified offline artifact, on its df8e4ee source archive with exact current
RTP modules and this increment. The focused run also passed 13 custody tests, including the
corrected genuine deletion-owner fixture, and the existing raw/retained receiver and CLI
contracts. Concurrent non-RTP provenance changes were preserved remotely but not overlaid
into that local test tree: these results are not full-head, all-target, Clippy or release
qualification. Repository-wide pre-existing formatting drift is not waived.

`scripts/check_rtp_decode.sh tests` includes the new targets alongside existing receipt,
receiver, recovery and CLI tests. No broader RTP bead, native platform matrix or release gate
is closed by this increment.
