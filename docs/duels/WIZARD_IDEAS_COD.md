Bundle these into one scheduled session whose preparation is already complete when the owner starts. Reuse the current registry, wait ledger, collectors, and preflight tools.

   | Device | Prepared owner interaction | Evidence that makes the interaction useful |
   |---|---|---|
   | Wyze `.39` | Preserve any working media session, confirm the selected update plan, and perform a supported power action when required by that plan. | Fresh identity, a device-originated update-stage receipt, and the canary acceptance results from recommendation 2. |
   | Wyze `.51` | Prepare the same deployment prerequisites, then proceed after the first unit’s compatible result. | Separate per-device receipts and hardware compatibility evidence. |

   Prepare the phone apps, account selection, physical access, stable power where supported, and the expected receipt for each step in advance. A charging cable is useful only if observation confirms that it changes the relevant availability window.

   For Owlet, first verify that the capture point actually sees the successful session. Use an authorized observation point with the required coverage, such as the operator’s AP/router capture facility when available. Retain sanitized metadata and protected evidence handles. Keep private credentials in their designated secret domain. A bounded first-boot receipt should identify the running firmware generation and each completed stage. A host-computed image hash anchors the intended bytes; retain device readback or the strongest available installation witness to establish what actually ran.

   This targets the controllable part of the firmware supply chain—the bytes and first-boot behavior we prepare. 3. **Resolve AOSU’s authorization path before spending more time on the OEM signer.**

   The fresh-registration runbook currently assumes that a new Tuya cloud-project ID/secret can replace the OEM app identity in the existing native signing harness. Tuya documents cloud-project credentials, account linking, and HMAC-SHA256 request signing. That supports a separate legitimate access path worth checking; it leaves compatibility with AOSU’s OEM `api.json` gateway unestablished. [Tuya cloud credentials and linking](https://developer.tuya.com/en/docs/developer/apply-cloud-api-key?id=Kff30z8sv62ah), [Tuya cloud request signing](https://developer.tuya.com/en/docs/iot/new-singnature?id=Kbw0q34cs2e5g).

   Start with a short supported entitlement diagnostic. Determine whether this owner’s AOSU account and exact camera/base can be linked to an authorized cloud project or supported OEM authorization flow in the correct region. If the platform supports it, verify the exact device identity through its normal authorized device-information operation. Tuya’s documented device-information response includes `local_key`; availability for this AOSU tuple still needs proof. Deposit any returned secret directly into the scoped secret backend and retain only the receipt and handle. [Tuya device-information contract](https://developer.tuya.com/en/docs/cloud/d00d20c097?id=Kag2xtiyewd3r).

   Preserve two competing explanations until evidence separates them. One is that supported cloud linking can provide the required device access. The other is that this OEM ecosystem requires vendor-supported authorization unavailable to the current project. The decisive observation is actual supported linking and an authorized response for this device. If linking is unavailable, persist that result and pursue the vendor’s account/support or export path. Creating more accounts and changing network identities cannot establish device entitlement.

   Keep `ILLEGAL_CLIENT_ID` as the observed response. The repository’s explanation that repeated registrations from one IP burned the registration remains a hypothesis unless the provider or controlled evidence confirms it. Record app identity, region, endpoint, SDK generation, and entitlement as possible discriminators. The offline signer result only establishes the tested input/output relation.

   If OEM signing remains necessary, first repair the existing vector runner’s specific evidence gap. It repeats one `selftest`, parses a printed `match`, and ignores each vector’s canonical input and expected signature as well as the child’s exit status. Require each vector’s exact comparison, an overall successful process result, and explicit executed negative cases. The current Docker base is also a mutable tag, so clean reproducibility remains a separate proof obligation. [Vector runner](deliverables/scripts/test_tuya_sign.py), [signer](deliverables/scripts/tuya_thing_sign.py), [Docker build](tools/thing-sign/Dockerfile.jvm).

   This ranks third because a short supported-platform check could eliminate a large amount of work in the wrong authorization domain. Confidence is high that the current assumption needs validation; success for this OEM account remains unknown. Completion is a proven scoped access path or a precisely documented unsupported entitlement, with the next legitimate enrollment branch identified.

4. **Turn existing telemetry into an opportunity scheduler for eligible enrollment and update work.**

   Represent each device’s next operation with its unmet prerequisites, fresh identity observation, expected opportunity event, attempt owner, deadline, and terminal proof. Subscribe to the telemetry already present. Distinguish reachable, authenticated, eligible for the selected update, transferring, rebooting, and serving media. These conditions can diverge on sleeping cameras. Keep effect ownership and cancellation under the existing FSS contracts.

   Prepare expensive host work ahead of time. When a real eligible event arrives, revalidate the prepared operation and consume the opportunity once. A durable per-device operation generation and fence should suppress duplicate work after restarts. An already dispatched operation is reconciled before another dispatch. Share a read-only view of AP, broker, forge, and observer health so a common outage produces one repair obligation and device-specific uncertainty.

   The existing reconciler already records the need to preserve healthy infrastructure because broker disruption can cause long camera backoff. Extend that behavior with explicit active-session witnesses where a proposed repair would interrupt a live transaction. Use fresh association/DHCP evidence and bounded responses for address resolution, followed by proper authentication for the actual operation. Old ARP entries remain weak presence evidence. [Reconciler](deliverables/scripts/fleet_reconcile.py), [identity registry](deliverables/fleet/registry.yaml).

   Learn timing from actual observed windows, preserving missed observations and censored durations. A camera that was never observed asleep does not provide a complete sleep-cycle sample. Begin with the simplest event rules and deadlines supported by recorded traces. Validate on held-out windows before using a fitted timing policy. Report eligible windows observed, operations completed, windows missed because preparation was late, time awake consumed, and operator interventions. Repeated observations within one boot/session share a failure domain.

   This ranks fourth because it improves the yield of future opportunities across the fleet, but cannot create missing credentials or LAN enrollment. Its main failure modes are false availability signals, duplicate dispatch, and a scheduler that becomes another competing controller. Reuse the current control plane and wait ledger. The first bounded evaluation should replay stale ARP, a missed wake, broker loss, restart during transfer, and an ambiguous completion through the deterministic reference before any live scheduling change. [Wait ledger](deliverables/scripts/wait_ledger.py), [registered effect and runtime requirements](AGENTS.md).

   Immediately after a device passes enrollment, run one bounded authenticated media acquisition through the existing first-party Rust entrypoint.    Use separate mandatory predicates for fresh authenticated administration, running firmware identity, media authentication, source receipt, decoded output where supported, and continuity. [Current proof definitions](deliverables/scripts/root_proof.py), [current aggregate status logic](deliverables/scripts/fleet_status.py).

   Make the local and remote paths independently visible. Verify local acquisition while the device is available, then test the existing tailnet acceptance row when remote enrollment is ready.    For sleeping devices, select event-driven acceptance with complete observed wake/clip episodes and explicit gaps. Continuous-camera and event-camera denominators differ.    This ranks fifth because it removes the delay between a successful enrollment and discovering that FSS still receives no useful evidence.
